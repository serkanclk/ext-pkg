# ING SQL Developer for VS Code - v2.6.0 Test Plan

This document outlines the testing strategy for the **v2.6.0** release of the ING SQL Developer extension. It highlights the focus areas, step-by-step test instructions, and potential impact areas where regressions might occur.

---

## 1. Feature Verification: Snippet Storage Migration

### Background
Snippets were migrated from VS Code's browser-bound `globalState` API to an explicit physical `snippets.json` file inside the extension's globally recognized storage path.

### Test Scenarios
1. **Fresh Installation:**
   - Install the new extension on a clean profile.
   - Add a snippet through the command palette or tree view.
   - Open a browser profile in Edge and reload VS Code — verify the snippet persists.
2. **Migration (Legacy Upgrade):**
   - Install the *previous* version of the extension and create a snippet.
   - Upgrade directly to v2.6.0.
   - The extension should seamlessly detect the legacy snippet and write to `snippets.json`. Verify the snippet is still visible in the Snippets view.
   - Create a new snippet and confirm both are preserved.

**Impact Areas**: Snippets panel, snippet insertion, tree hierarchy loading.

---

## 2. Feature Verification: Package Body in Object Browser

### Background
Oracle Packages now unpack into two child nodes: `Spec` and `Body`.

### Test Scenarios
1. Navigate to the Object Browser panel.
2. Expand the `Packages` folder of a schema containing valid packages.
3. Click to expand a package node. Verify two children appear: `Spec` and `Body`.
4. Right-click the **Spec** node:
   - "View Source", "Compile", and "Drop" should operate strictly on the `PACKAGE` specification.
5. Right-click the **Body** node:
   - "View Source", "Compile", and "Drop" should operate strictly on the `PACKAGE BODY`.

**Impact Areas**: Context menus in Object Browser, compiler commands, dropping operations.

---

## 3. Feature Verification: SQL Diagnostics & Error Positioning

### Background
The extension now offers real-time syntax checking (red squiggly lines) for string literals and parentheses, and will map Oracle execution errors to character positions in the script.

### Test Scenarios
1. **Typing / Real-time Checks:**
   - Open a new `.sql` worksheet.
   - Type `SELECT * FROM table WHERE col = 'value`. (Omit the last quote). Wait 500ms. Verify a red squiggly appears.
   - Type `SELECT (1 + 2 FROM dual;`. Wait 500ms. Verify a red squiggly implies a missing parenthesis.
   - Close the quote or missing parenthesis. Verify the line clears itself.
2. **Oracle Execution Errors:**
   - Connect to a database.
   - Execute a multi-line query that introduces a semantic error (e.g., `SELECT * FROM NON_EXISTENT_TBL`).
   - The query will fail. Verify a red squiggly line marks the token `NON_EXISTENT_TBL` in the editor.
   - Hover over the error in the editor. Verify the full Oracle `ORA-00942` message is displayed alongside the "Oracle" source text.
   - Clear the error by making any text edit on the line or running a successful query.

**Impact Areas**: Document sync performance, statement offset calculations, `executeScript` offsets, VS Code Problems Panel spam.

## 4. Feature Verification: Smart Context-Aware IntelliSense

### Background
We built a custom lightweight SQL string parser to detect database context and suggest columns dynamically.

### Test Scenarios
1. **Table Context (`FROM`)**:
   - Type `FROM ` or `JOIN `. The suggestions list should heavily favor Table and View completions.
2. **Schema Dot (`SCHEMA.`)**:
   - Type `SYS.` or `HR.`. The system should silently spin up a connection lookup and return tables matching the prefix. Connect to a valid schema and test. Disconnect and re-test (it should handle the failure gracefully by returning nothing).
3. **Column Prefix (`ALIAS.`)**:
   - Type `SELECT a. FROM hr.employees a`. Immediately after typing the dot (`a.`), grid columns for `hr.employees` (e.g., `EMPLOYEE_ID`) must appear automatically with type details (e.g., `NUMBER(6) NOT NULL`).
4. **General Clause Context (`SELECT` / `WHERE`)**:
   - Type `SELECT ` then put your cursor before the `FROM hr.employees`. It should suggest `hr.employees` columns.
   - Type `WHERE `. It should suggest columns and standard SQL functions.
   - No cross-pollution: Typing `WHERE` should *not* aggressively suggest generic datatypes (`VARCHAR2`).

**Impact Areas**: Memory usage tracking / IntelliSense lag, general typing lag (watch for `ColumnCacheService` failing to lazy load properly).

## 5. Feature Verification: View Configuration (Null Display & Font)

### Background
Results Grid now listens to VS Code styling updates dynamically and injects null customization without a panel reboot.

### Test Scenarios
1. **Null Display (`ingSql.resultGrid.nullDisplay`)**:
   - Query a table with empty/null fields.
   - Go to VS Code Settings → `ingSql.resultGrid.nullDisplay`. Enter `MISSING_DATA`.
   - Ensure the open grid immediately updates all `(null)` cells to `MISSING_DATA` without reloading the tab.
   - Perform a CSV export and an HTML export. Both should print `MISSING_DATA`.
   - Perform a JSON and SQL export. They must preserve their native formats (`null` and `NULL`).
2. **Editor Font Hook (`ingSql.resultGrid.useEditorFont`)**:
   - Go to VS Code Settings → `editor.fontFamily`. Set it to an obvious font (e.g., `Courier New` or `Comic Sans MS`).
   - Run a query. Observe the font.
   - Go to VS Code Settings → `ingSql.resultGrid.useEditorFont`. Toggle it OFF. The font should revert to standard VS Code UI web-sans fonts.
   - Toggle it ON. It should revert back to your custom Editor Font.

**Impact Areas**: CSS rendering lag, Export Service breaking non-compatible formats (XLSX stringification), large dataset filtering bugs.

---

## ⚠️ Known Impact Considerations for Testers

1. **Large Schemas (IntelliSense Cache)**: Because IntelliSense caches tables locally via `ColumnCacheService` upon first hover/dot lookup, large schemas (+10,000 tables) might pause the IntelliSense loading spinner (`...`) on the very first keystroke of a query. Testers should simulate pulling a large table definition to ensure no application freezes or crashes (OOM errors) occur.
2. **Offset Tracking (`SqlContextParser.ts`)**: The parser that figures out which row a Syntax error occurs on has been heavily modified. Testers must run large scripts (using the `Execute Script (F5)` function) mimicking 1,000+ line blocks to ensure the offset arrays map properly and don't mistakenly underline the wrong lines.
